# WORKFLOW:AI 工作流程

## 1. 任务分级

| 级别 | 例子 | 要求 |
|---|---|---|
| S(小) | 改一个 bug、加一个测试、改文案 | 直接做,汇报即可 |
| M(中) | 新增一个功能点、新增一个 action | 先给计划,可不等确认,做完汇报 |
| L(大) | 新模块、改数据结构、改线程模型、跨平台抽象 | **先给计划并等用户确认**,再分多个提交实现 |

拿不准级别时按高一级处理。

## 2. 标准流程

### 2.1 开始前
1. 读 `AGENTS.md`、本文件,以及任务相关的文档(见 AGENTS.md 索引)。
2. 读相关现有代码,确认现状,不要假设。
3. 涉及第三方 crate 的 API:先在锁定版本源码中查证(硬性规则 1)。
4. 涉及用户可见行为:找到 `BEHAVIOR_SPEC.md` 里对应的条目 ID。找不到条目 = 规格缺失,先问。

### 2.2 计划(M/L 级必写)
```
目标:一句话
改动范围:文件/模块列表
方案:3-8 行
不做什么:明确排除项
风险与平台差异:Windows / Linux 各有什么要注意
验证方式:跑哪些测试、手工验收哪些条目
```

### 2.3 实现
- 每一步结束时项目都应能编译。
- 一个提交只做一件事;提交信息格式:`模块: 动词开头的简述`(如 `selection: 左键抬起时写入选择缓冲区`)。
- 公共接口变更必须同步更新相关文档和测试。
- 发现任务范围外的问题:记录到汇报的"发现的其他问题",**不要顺手修**。

### 2.4 验证
- 运行 AGENTS.md 第 5 节的命令。
- 行为类改动:运行对应测试,并对照 `TESTING.md` 的手工验收清单列出哪些已验、哪些需要用户手工验。
- AI 无法运行图形界面时,**必须明说"UI 行为未实际运行验证"**,不得根据代码推断来声称"已验证"。

## 3. 完成定义(Definition of Done)

全部满足才算完成:
- [ ] 代码编译,`fmt` / `clippy -D warnings` / `test` 通过(或已说明为何未运行)
- [ ] 新增行为有对应测试;测试名或注释包含 `BEHAVIOR_SPEC` 条目 ID
- [ ] 没有新增 `unwrap()` / `expect()`(测试代码除外)、没有未说明的 `TODO`
- [ ] Windows 与 Linux 的 `cargo check` 均通过,或已说明阻塞原因
- [ ] 没有修改范围外的文件
- [ ] 文档已同步(若接口、行为或架构有变化)
- [ ] 已按模板汇报

## 4. 汇报模板

```
## 完成情况
做了什么(1-5 条)

## 验证
- 已运行:命令 → 结果
- 未运行:命令 → 原因
- 需要用户手工验证:BEHAVIOR_SPEC 条目 ID 列表

## 与规格/计划的偏差
(没有就写"无")

## 风险与待确认
(包括平台差异、未验证的 API 假设、性能担忧)

## 发现的其他问题
(未处理,仅记录)
```

## 5. 必须停下来问用户的情形

- 规格缺失、冲突或看起来有误
- 需要新增依赖、升级依赖、改工具链
- 需要改动 `ARCHITECTURE.md` 中的不变量
- 需要 `unsafe`
- 第三方 API 在锁定版本中找不到预期的能力
- 测试失败,且原因不明,尝试两次仍未解决
- 任务实际规模明显超出最初判断

## 6. 禁止的行为模式

- **假装完成:** 没跑过的命令说成跑过;没实现的部分用占位代码蒙混。
- **静默降级:** 实现不了某个要求,却在汇报里不提。
- **过度设计:** 为"将来可能"加抽象、加配置项、加泛型。只实现当前阶段需要的。
- **范围蔓延:** 借任务之名重写无关模块。
- **复述式汇报:** 把 diff 逐行翻译成文字。汇报讲结果和风险,不讲流水账。
