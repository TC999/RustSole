# CODING_STANDARDS:编码规范

## 1. 基本要求

- 使用仓库根目录 `rust-toolchain.toml` 指定的工具链,不自行更改。
- 必须通过:`cargo fmt`、`cargo clippy --workspace --all-targets -- -D warnings`。
- 默认不使用 `#[allow(...)]`。确需使用时,必须同一行注释原因,并在汇报中列出。

## 2. 第三方 API 使用

1. GPUI 与 `alacritty_terminal` 的 API 以**仓库锁定的版本**为准,不以记忆、旧文档或网络上的示例为准。
2. 使用某个 API 前,先在依赖源码里找到它的定义。找不到就不要用,改为向用户说明。
3. 如果参考了 Zed 的某个实现,只在注释里写"参考思路",不得复制代码(见 `LICENSING.md`)。
4. 引用易变 API 的位置,加注释 `// API: gpui <版本号>`,方便升级时批量检查。

## 3. 错误处理

- 库 crate:用 `thiserror` 定义具体错误类型;应用入口:用 `anyhow`。
- 非测试代码**禁止** `unwrap()` / `expect()`。唯一例外:逻辑上不可能失败且附注释说明原因。
- 不吞错误。`let _ =` 只用于"失败也无影响"的场景(如向已关闭的 channel 发送),并在上方注释说明。
- 用户可恢复的错误(配置解析失败、Profile 启动失败)显示在界面上,不 panic。

## 4. 日志

- 使用 `tracing`,不使用 `println!` / `eprintln!`(测试除外)。
- 不得记录终端输出内容、粘贴内容、选中文本(可能含密码和密钥)。只记录长度、类型等元信息。

## 5. 并发与锁

- 持锁期间不得:`await`、做 I/O、调用 GPUI 上下文、调用可能再次获取同一把锁的函数。
- 锁内取出需要的数据,立即释放;之后再处理。
- 不得在多把锁之间随意嵌套;确需嵌套时,在模块文档里写明加锁顺序。
- 跨线程共享的数据优先使用 channel 传递所有权,其次才是 `Arc<Mutex<_>>`。

## 6. GPUI 约定

- 状态放在 `Entity` 中,通过 `update` 修改;改了影响显示的状态后调用 `cx.notify()`。
- 事件处理函数里只做"解析事件并分发到 Action/方法",不写长逻辑。
- 不在主线程做阻塞操作。耗时工作用 `cx.background_spawn` 或独立线程。
- 渲染热路径(`prepaint` / `paint`)中:不分配大对象、不重复计算布局、不每帧重新 shape 未变化的文本。
- 需要自绘(Element)的地方才自绘;普通界面(菜单、对话框、标签栏)用组合 `div`。
- 颜色、间距、字号来自主题/配置,不在组件内硬编码。

## 7. 平台代码

- `cfg(target_os)` 仅在 `term_platform` 内出现(硬性规则 6)。
- 平台差异通过 trait 暴露,例如:

```rust
pub trait SelectionBackend {
    fn set(&self, text: String);
    fn get(&self) -> Option<String>;
}
```

- 每个平台实现都要有对应的编译检查;某平台暂不支持的功能,返回明确的 `Unsupported` 而不是静默什么都不做。

## 8. 命名与结构

- 类型 `UpperCamelCase`,函数/变量 `snake_case`,常量 `SCREAMING_SNAKE_CASE`。
- 函数不超过约 60 行;超过时按职责拆分。
- 一个文件一个主要职责,不超过约 500 行;超过时拆模块。
- 公共项必须有文档注释(`///`),说明用途、前置条件、会在什么情况下失败。
- 注释写"为什么",不写"做了什么"。涉及终端协议的地方写明依据(如转义序列名称)。

## 9. 性能

- 没有度量依据,不做"优化"。优化必须附带前后对比数据。
- 但以下是**必须遵守**的基本做法:合并相邻同样式文本 run、节流 Wakeup、锁内只取快照。

## 10. 安全

- 粘贴内容、拖入的文件路径、超链接目标都视为不可信输入,按 `BEHAVIOR_SPEC.md` 的 `PASTE-*` 规则处理。
- 构造要发给子进程的命令时,不拼接字符串交给 shell 执行;使用参数数组。
- 不读取或上传与任务无关的用户文件。
